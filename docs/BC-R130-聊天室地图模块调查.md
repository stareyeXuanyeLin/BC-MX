# BC R130 聊天室地图模块调查

## 1. 文档目的

本文记录 Bondage Club R130 聊天室地图功能的源码结构、数据模型、网络同步、导入导出与持久化机制，为“将聊天室地图保存到本地并管理”的插件开发提供依据。

当前阶段只调查原版实现并确定插件边界，不包含具体插件界面和业务代码。

## 3. 模块职责

### 3.1 `ChatRoomMapView.js`

地图功能的核心模块，负责：

- 40×40 地图初始化；
- 地块、物件和效果定义；
- 地图绘制与视野、听觉遮罩；
- 玩家移动、碰撞与物件交互；
- 地图编辑、撤销和延迟同步；
- `/mapcopy`、`/mappaste` 的底层实现；
- `ChatRoomMapManager` 与版本化地图编码。

### 3.2 `ChatRoom.js`

聊天室生命周期与地图的连接层，负责：

- 保存和替换 `ChatRoomData`；
- 处理 `ChatRoomSyncRoomProperties`；
- 从房间设置中提取 `MapData`；
- 激活地图视图；
- 保存 `Player.LastChatRoom`；
- 在地图属性变化后通知地图视图。

### 3.3 `ChatAdmin.js`

负责创建和更新聊天室。地图房创建时，如果 `Tiles` 或 `Objects` 缺失，会调用：

```js
ChatRoomMapViewInitialize(type)
```

创建默认地图，再随 `ChatRoomCreate` 或 `ChatRoomAdmin` 请求发送给服务器。

### 3.4 `ChatSearch.js`

负责聊天室搜索、自动返回上次房间，以及原房间不存在时的重建流程。

当玩家满足返回设置且原房间消失时，新房间会使用：

```js
MapData: Player.LastChatRoom.MapData
```

### 3.5 `CommandsDefault.js`

注册原版命令：

```text
/mapcopy
/mappaste
```

分别调用：

```js
ChatRoomMapViewCopy();
ChatRoomMapViewPaste(mapString);
```

## 4. 地图数据分层

聊天室地图相关数据分为房间级数据和角色级数据。插件必须严格区分二者。

## 4.1 房间级地图数据

当前聊天室的地图本体位于：

```js
ChatRoomData.MapData
```

类型：

```ts
interface ServerChatRoomMapData {
    Type: ChatRoomMapType;
    Fog?: boolean;
    Tiles?: string;
    Objects?: string;
    Effects?: string;
}
```

字段含义：

| 字段 | 含义 |
|---|---|
| `Type` | 地图显示模式：`Always`、`Hybrid`、`Never` |
| `Fog` | 是否启用原版迷雾 |
| `Tiles` | 地块 ID 数组的字符串编码 |
| `Objects` | 物件 ID 数组的字符串编码 |
| `Effects` | 灯光与阴影效果的版本化二进制编码 |

地图尺寸固定为：

```js
ChatRoomMapViewWidth = 40;
ChatRoomMapViewHeight = 40;
```

标准地图共有：

```text
40 × 40 = 1600
```

个位置，因此 `Tiles` 和 `Objects` 正常长度均为 1600 个 UTF-16 代码单元。

读取某个位置时，原版使用：

```js
const id = encoded.charCodeAt(index);
```

再通过查找表获得运行时定义：

```js
ChatRoomMapViewTileLookup[id]
ChatRoomMapViewObjectLookup[id]
```

这意味着字符串本质上是紧凑的二维整数数组，不应按普通文本处理。

## 4.2 角色级地图状态

角色在地图中的状态位于：

```js
Character.MapData
Player.MapData
```

类型：

```ts
type ChatRoomMapData = {
    Pos: {
        X: number;
        Y: number;
    };
    PrivateState: {
        HasKeyBronze?: boolean;
        HasKeySilver?: boolean;
        HasKeyGold?: boolean;
        [key: string]: any;
    };
};
```

它只描述：

- 角色当前位置；
- 角色持有的地图钥匙；
- 可扩展的个人地图状态。

本地地图库保存的是房间地图本体，不应把 `Player.MapData` 当作地图文件的一部分。

## 5. 地块、物件与效果

### 5.1 地块

地块运行时定义为 `ChatRoomMapTile`，主要类型包括：

```text
Floor
FloorExterior
Wall
Water
```

定义可附带：

- 透明度；
- 视线阻挡；
- 听觉阻挡；
- 进入条件；
- 进入事件。

### 5.2 物件

物件运行时定义为 `ChatRoomMapObject`，主要类别包括：

```text
FloorDecoration
FloorDecorationThemed
FloorDecorationParty
FloorDecorationCamping
FloorDecorationExpanding
FloorItem
FloorObstacle
FloorNumber
FloorLetter
FloorIcon
WallDecoration
WallPath
Banners
```

物件可附带：

- 图片位置与尺寸；
- 入口或出口语义；
- 唯一性约束；
- 互动 Asset；
- 视线与听觉阻挡；
- 动态可见性；
- 进入条件和进入事件。

### 5.3 效果

R130 当前公开的效果类型为：

```ts
interface ChatRoomMapEffectStaticLighting {
    Type: "StaticLighting";
    TypeId: 1;
    ID: number;
    Color: [number, number, number, number];
}
```

效果数据由 `ChatRoomMapManager.Map` 维护，并编码进：

```js
ChatRoomData.MapData.Effects
```

## 6. 地图初始化

原版初始化入口：

```js
ChatRoomMapViewInitialize(mode)
```

默认结果：

```js
{
    Type: mode,
    Tiles: defaultMap,
    Objects: defaultMap,
    Effects: undefined,
}
```

`defaultMap` 是长度为 1600 的默认 ID 字符串。

创建或更新房间时，`ChatAdmin.js` 会保证启用地图的房间至少拥有 `Tiles` 和 `Objects`。

## 7. 地图编辑与服务器同步

地图编辑主要通过以下函数发生：

```js
ChatRoomMapViewMouseDown
ChatRoomMapViewMouseMove
ChatRoomMapViewMouseUp
ChatRoomMapViewClick
```

地块和物件编辑直接修改：

```js
ChatRoomData.MapData.Tiles
ChatRoomData.MapData.Objects
```

效果编辑调用：

```js
ChatRoomMapManager.Map.setEffectsByIndex(...)
ChatRoomMapManager.Map.updateGlobalMapData()
```

修改完成后调用：

```js
ChatRoomMapViewUpdateFlag()
```

它会：

1. 清理与地块类型不兼容的物件；
2. 设置延迟同步标志；
3. 大约五秒后由 `ChatRoomMapViewUpdateRoomSync()` 更新房间。

最终发送：

```js
ServerSend("ChatRoomAdmin", {
    MemberNumber: Player.ID,
    Room: ChatRoomGetSettings(ChatRoomData),
    Action: "Update",
});
```

地图修改属于房间级操作，只有管理员能够把恢复的地图写入当前房间。

## 8. 地图属性接收流程

服务器推送房间属性时，主要流程为：

```text
ChatRoomSyncRoomProperties
    ↓
替换 ChatRoomData
    ↓
ChatRoomMapViewInitializeCharacter(Player)
    ↓
ChatRoomRefreshActiveView
    ↓
ChatRoomActiveView.RoomUpdated
    ↓
ChatRoomMapViewRoomUpdated
    ↓
ChatRoomMapManager.OnMapDataUpdated
```

`OnMapDataUpdated()` 会从 `ChatRoomData.MapData.Effects` 重新解码内部效果状态。

插件在监听房间地图变化时，可以关注：

```js
ChatRoomSyncRoomProperties
ChatRoomMapViewRoomUpdated
```

但显式保存功能无需持续监听，只需在用户保存时读取当前地图。

## 9. 原版地图导出

原版命令：

```text
/mapcopy
```

调用链：

```text
ChatRoomMapViewCopy
    ↓
ChatRoomMapManager.Map.exportString
    ↓
ExportMap
```

插件应把：

```js
ChatRoomMapManager.Map.exportString()
```

返回的字符串视为标准地图文件负载。

### 9.1 R130 导出结构

R130 导出结果由两部分组成：

```text
旧式地图主体 + @ + 版本化 BitString 数据
```

常量：

```js
const MAP_EXPORT_VERSION_TAG = "@";
const MAP_SYNC_VERSION_BIT_SIZE = 8;
const MAP_SYNC_CURRENT_VERSION = 0;
const CURRENT_EFFECTS_CODEC_VERSION = 0;
```

旧式主体包含：

```text
Type
Fog
Tiles
Objects
```

处理方式：

```text
JSON.stringify
    ↓
LZString.compressToBase64
```

`Effects` 不重复放入旧式主体，而是通过版本化 BitString 编码后附加在 `@` 后面。

### 9.2 为什么必须保存原版导出字符串

直接保存：

```js
JSON.stringify(ChatRoomData.MapData)
```

当前版本可能暂时可用，但会绕过：

- 原版 Codec 版本号；
- 老地图兼容逻辑；
- 新旧数据组合格式；
- 未来地图结构迁移。

原版源码明确表示地图编码模块仍会继续演进，未来 `Tiles` 和 `Objects` 也可能迁入 `ChatRoomMapManager`。

因此插件的长期稳定策略是：

```text
插件负责保存和组织原版导出字符串
BC 负责地图格式、校验、编码和迁移
```

## 10. 原版地图导入

原版命令：

```text
/mappaste
```

调用链：

```text
ChatRoomMapViewPaste
    ↓
ChatRoomMapManager.Map.importString
    ↓
DecodeExportedMap
```

导入器支持：

- 没有 `@` 的旧版 LZString 地图；
- 旧式主体与新版效果组合的地图；
- 版本化 BitString 解码；
- 尽量恢复可识别的数据部分。

成功后，原版继续调用：

```js
ChatRoomMapViewUpdateFlag();
ChatRoomMapViewCalculatePerceptionMasks();
```

`ChatRoomMapViewPaste()` 自带管理员权限检查和本地提示。

## 11. `ChatRoomMapManager`

核心对象：

```js
ChatRoomMapManager.Map
```

与本地地图保存最相关的方法：

```js
exportString()
importString(mapString)
loadGlobalMapData()
updateGlobalMapData()
```

内部还包含：

- `MapData` 类；
- 效果数组；
- DirtyFlags；
- 多版本 Codec；
- BitString 编解码器。

原版注释明确提示该模块仍在演进，模组作者应尽量避免依赖内部实现。

插件应将直接依赖限制在：

```js
exportString()
importString()
```

不要依赖：

```text
_mapData
_dirtyFlags
MapEffectsCodecs
MapDataCodecs
内部效果数组结构
```

## 12. 原版持久化边界

### 12.1 活动聊天室

活动地图随服务器内存中的聊天室对象存在。空房间消失后，不存在面向普通玩家的永久房间地图仓库。

### 12.2 `Player.LastChatRoom`

启用“返回上次聊天室”后，客户端会保存：

```js
Player.LastChatRoom = ChatRoomGetSettings(room)
```

其中包括：

```js
Player.LastChatRoom.MapData
```

该值用于玩家重新登录时加入或重建上次房间。

它是单个“上次房间快照”，不属于地图历史库。进入其他房间后可能被覆盖，相关设置或搜索流程也可能将其清空。

### 12.3 `Player.LastMapData`

只保存人物位置和个人地图状态，不能恢复房间地图本体。

### 12.4 原版查询接口

原版 `AccountQuery` 只支持：

```text
EmailStatus
EmailUpdate
OnlineFriends
```

没有公开的历史聊天室或历史地图查询接口。

## 13. 插件建议的数据模型

建议把原版导出字符串作为不可解释的标准负载，外层只添加插件自己的管理信息：

```ts
interface LocalMapRecord {
    id: string;
    name: string;
    createdAt: number;
    updatedAt: number;

    /** BC 原版 exportString() 返回值 */
    payload: string;

    /** 仅用于列表与提示，不参与地图解码 */
    sourceRoomName?: string;
    mapType?: "Always" | "Hybrid" | "Never";
    note?: string;

    /** 插件本地存储格式版本 */
    storageVersion: number;
}
```

其中：

- `payload` 是唯一地图真值；
- 名称、来源、备注和时间属于插件元数据；
- 插件不自行拆解或改写 `payload`；
- 导入合法性由 BC 原生导入器判断。

## 14. 推荐的功能边界

### 14.1 保存

保存前检查：

```js
ChatRoomData?.MapData
ChatRoomData.MapData.Type !== "Never"
ChatRoomPlayerIsAdmin()
```

然后调用：

```js
ChatRoomMapManager.Map.exportString()
```

按照最终产品权限要求，保存当前房间地图与用当前地图覆盖本地存档都要求玩家是当前房间管理员。界面状态和业务执行层均需检查，避免在非管理员房间采集或操作当前地图。

### 14.2 加载

加载属于会修改整个房间的操作，应要求：

- 当前处于地图房；
- 当前玩家是房间管理员；
- 用户明确确认覆盖；
- 当前地图已先备份；
- 导入失败时不继续同步。

可以优先复用：

```js
ChatRoomMapViewPaste(payload)
```

如果插件需要明确的布尔返回值，可调用：

```js
ChatRoomMapManager.Map.importString(payload)
```

成功后复用原版后处理：

```js
ChatRoomMapViewUpdateFlag();
ChatRoomMapViewCalculatePerceptionMasks();
```

### 14.3 本地存储

初期可选择：

- `localStorage`：实现简单，适合少量地图；
- IndexedDB：适合更稳健的记录管理、索引和未来扩展；
- 手动导入导出插件数据：用于跨设备迁移和备份。

地图负载本身通常不大，但插件仍应：

- 对总记录数和容量做提示；
- 写入失败时保留当前状态；
- 导入插件备份时使用事务式校验；
- 不在校验成功前覆盖现有地图记录。

## 15. 候选 Hook 点

| 目标 | 候选入口 | 建议 |
|---|---|---|
| 显式保存当前地图 | `ChatRoomMapManager.Map.exportString` | 直接调用，无需 Hook |
| 加载到当前房间 | `ChatRoomMapViewPaste` | 优先复用原版流程 |
| 判断地图是否发生编辑 | `ChatRoomMapViewUpdateFlag` | 仅在需要脏状态提示时 Hook |
| 感知服务器房间属性变化 | `ChatRoomSyncRoomProperties` | 用于刷新插件状态 |
| 感知地图管理器重载 | `ChatRoomMapViewRoomUpdated` | 可作为地图变化通知 |
| 地图视图 UI | `ChatRoomMapViewDrawUi`、`ChatRoomMapViewClick` | 后续确定交互方案后再接入 |
| 聊天命令 | `CommandsDefault` 的注册模式 | 可新增简短命令作为备用入口 |

显式保存与加载已经有稳定入口，第一版不需要自动拦截所有地图编辑行为。

## 16. 主要风险

### 16.1 上游接口演进

`ChatRoomMapManager` 仍在开发中。插件应减少对内部类和字段的耦合，并在 BC 更新后检查：

```js
ChatRoomMapManager?.Map?.exportString
ChatRoomMapManager?.Map?.importString
```

### 16.2 覆盖当前房间

地图加载会影响房间内所有玩家。界面必须明确显示：

- 将覆盖哪个房间；
- 载入哪张本地地图；
- 当前地图是否已备份；
- 是否具备管理员权限。

### 16.3 部分恢复语义

原版解码器倾向于尽可能恢复兼容部分。插件不应仅凭字符串包含 `@` 就判断地图完整，应以原版导入结果为准。

### 16.4 原始对象与原版导出串混用

插件的正式地图记录应只接受原版导出串。裸 `MapData` JSON 可作为应急恢复输入，但应在临时房间恢复后重新通过 `/mapcopy` 或 `exportString()` 转为标准负载。

### 16.5 存储损坏

本地数据库应采用：

- 版本号；
- 数据结构校验；
- 写入前深拷贝；
- 导入前完整验证；
- 失败不覆盖；
- 可导出的人工备份。

## 17. 第一版开发建议

建议第一版只实现最小闭环：

1. 保存当前地图；
2. 显示本地地图列表；
3. 重命名、备注、删除；
4. 加载地图前确认并备份当前地图；
5. 导出单张插件地图文件；
6. 导入单张插件地图文件或原版地图字符串；
7. 导出和导入插件本地地图库；
8. 提供按 ID、按名称、保留双方、跳过和整库替换等冲突策略；
9. 明确报告权限、容量、解析和写入错误；
10. 玩家位置继续使用 BC 原版碰撞修正，不作为地图加载成功条件。

暂不实现：

- 地图格式二次编码；
- 地块级差异比较；
- 自动云同步；
- 自动保存每一次编辑；
- 修改原版 Codec；
- 依赖地图素材图片的自制预览渲染器。

## 18. 待确认设计问题

正式编码前还需要确定：

1. 插件正式名称和用户可见名称；
2. 使用 `localStorage` 还是 IndexedDB；
3. 地图库入口放在地图视图、聊天命令还是独立浮层；
4. 加载前当前地图的自动备份保留策略；
5. 删除地图是否进入回收站；
6. 地图记录是否支持标签和搜索；
7. 插件地图库的跨设备导入导出格式；
8. 是否需要保存房间地图模式与迷雾作为独立展示元数据；
9. BC 更新后如何做 API 能力检测与降级提示。
