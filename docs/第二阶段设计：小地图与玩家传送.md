# 第二阶段设计：小地图与玩家传送

## 1. 目标

在 BC Map Saver 第一阶段（地图存档/加载）基础上新增两个能力：

1. **小地图**：实时显示当前房间地图的可通行区域（地面）与不可通行区域（墙壁/障碍），并标出所有玩家位置。支持滚轮缩放与拖拽平移，可查看任意局部区域。
2. **玩家位置操作**：房间管理员可以通过小地图把任意玩家（包括自己）挪到指定格子。

本阶段不改动第一阶段的地图存档逻辑，两个能力是独立模块，共用同一份地图数据读取层。

## 2. 关键结论（源码调查）

参考基线：`参考源码/Bondage-College-master`，`GameVersion = "R130"`。

### 2.1 小地图数据全部来自公开结构，无需破解内部实现

| 数据 | 来源 | 说明 |
|---|---|---|
| 地图尺寸 | `ChatRoomMapViewWidth/Height` | 固定 40×40 |
| 地块编码 | `ChatRoomData.MapData.Tiles` | 1600 个 UTF-16 代码单元，`charCodeAt(i)` 得到 Tile ID |
| 物件编码 | `ChatRoomData.MapData.Objects` | 同上 |
| Tile 定义 | `ChatRoomMapViewTileLookup[id]` | `{ Type, Style, CanEnter, BlockVision }` |
| Object 定义 | `ChatRoomMapViewObjectLookup[id]` | 同上，另含绘制偏移 |
| 墙壁判定 | `ChatRoomMapViewIsWall(X, Y)` | **Tile ID ∈ [1000, 2000) 即为墙**，一行代码即可复刻 |
| 玩家位置 | `Player.MapData.Pos`（自己）、`ChatRoomCharacter[i].MapData?.Pos`（他人） | 位置由服务器广播，客户端每帧扫描即可 |

原版渲染走 `ChatRoomMapViewDrawGrid()` 的 Canvas 图片管线，插件**不复用**，改为独立 DOM `<canvas>`，避免污染原版绘制（沿用第一阶段 `bms-` DOM 方案）。

### 2.2 传送：原版 R130 已内置管理员传送，不用自己发明协议

这是本次调查最重要的发现。原版 `ChatRoomMapView.js` 已有完整实现：

```js
// 发送端（管理员调用）
function ChatRoomMapViewTeleport(target, position) {
    if (!ChatRoomPlayerIsAdmin()) return;
    if (Player.MemberNumber === target.MemberNumber) Player.Position = position;
    const dictionary = new DictionaryBuilder().mapViewTeleport(position).build();
    ServerSend("ChatRoomChat", { Content: "ChatRoomMapViewTeleport", Type: "Hidden",
        Dictionary: dictionary, Target: target?.MemberNumber });
}
```

完整链路（全部是原版代码，**被挪的玩家不需要安装任何插件**）：

```text
管理员: ChatRoomMapViewTeleport(target, pos)
    ↓ ServerSend("ChatRoomChat", Hidden + Target 定向)
服务器: 将 Hidden 消息只转发给 Target（成熟机制，RuleInfoGet/TakeSuitcase 同款）
    ↓
目标客户端: ChatRoomMessageProcessHidden → ChatRoomMapViewTeleportHiddenMessage
    ↓ 校验 sender 是管理员（ChatRoomCharacterIsAdmin）
目标客户端: Player.Position = pos（setter 自带校验 + 触发同步标志）
    ↓ 约 1 秒后
目标客户端: ServerSend("ChatRoomCharacterMapDataUpdate", Player.MapData) → 广播给全房间
```

要点：

- 位置校验是结构校验（`ServerAccountDataSyncedValidate.MapData.Pos`），**传送无视碰撞**，这是原版管理员语义；
- 接收端只查 sender 是否管理员，不查目标，安全性由"服务器只把带 Target 的 Hidden 消息转发给目标"保证；
- 传送自己时原版本地立即生效；
- `Player.Position` setter 会调用 `ChatRoomMapViewCalculatePerceptionMasks()` 并置更新标志，同步全自动，插件零后处理。

### 2.3 可通行性判定（静态网格）

原版 `ChatRoomMapViewPositionIsBlocked(X, Y)` 依赖"玩家当前站在哪个格子"来推导方向（门只能从正面进），不能直接用于静态渲染。静态判定策略：

对格子 P，模拟从 4 个邻居进入：方向 `dir` 由邻居相对 P 的位置决定，调用

```js
tile.CanEnter(dir)   // Wall / HalfWall 恒 false；地板多数无 CanEnter（视为可入）
obj.CanEnter(dir)    // FloorObstacle 类恒 false；门按方向
```

任一方向返回 true（或没有 CanEnter 函数）→ P 标记为可通行。1600 格 × 4 方向 = 最多 6400 次调用，只在地图变化时算一次，无性能问题。该方案完全复用原版语义，门、半墙、栅栏、雕像等都能正确判定。

另注意 `HalfWall`（Tile ID 199，Type 是 "Floor" 但 `CanEnter: () => false`）和 `FloorObstacle` 族（床、椅子、雕像、围栏等，ID ≥ 2000 且 `CanEnter: () => false`）都会挡路，不能只用"ID ≥ 1000 是墙"一条规则。

## 3. 小地图设计

### 3.1 模块划分

沿用 build.ps1 的按序合并结构，新增独立文件避免膨胀 05-ui.js：

```text
00-userscript-header.js
01-runtime.js
02-storage.js
03-exchange.js
04-map-bridge.js      ← 增加 buildMapGridSnapshot / teleportCharacter
05-minimap.js         ← 新增：小地图渲染与交互
06-ui.js              ← 原 05-ui.js 改名？否：保持文件名，06 位置插入
06-bootstrap.js
```

更稳妥的做法：不改现有文件名，`build.ps1` 的 parts 数组插入 `'05-minimap.js'`，原 `05-ui.js` 与 `06-bootstrap.js` 顺延文件名不变（数组顺序即合并顺序，文件名不必与序号严格对应）。为避免歧义，直接改名为 `06-ui.js`、`07-bootstrap.js` 并同步 build.ps1 与测试引用亦可，二者等价。

### 3.3 渲染层（05-minimap.js）

- **DOM 结构**：悬浮面板（`position: fixed`，右上角可折叠），内部一个 `<canvas>` + 控制条（缩放 +/-、复位、关闭）；
- **底图缓存**：离屏 canvas 画 40×40 色块网格（地面浅色系、墙深色、水蓝色、障碍深灰、半墙中灰），带 1px 网格线和图例；地图变化才重画，平时直接 blit；
- **玩家层**：250ms 节流扫描 `Player + ChatRoomCharacter` 的位置表，与上次快照比较，变化才重绘。玩家渲染为圆点，自己白色描边高亮，hover 显示昵称；
- **视口变换**：`{ zoom, panX, panY }`，滚轮缩放（以鼠标位置为锚点，clamp 0.5×~8×），按住拖拽平移，双击复位；
- **显隐**：`isMapRoom()` 且处于聊天室地图视图时显示开关按钮（普通玩家可见，不要求管理员）；非地图房自动隐藏；
- **迷雾**：第一版显示全图（小地图是概览工具），不做视野联动，接口预留。

### 3.4 与存档 UI 的关系

- 小地图是**独立浮窗**，与存档面板（openUI）互不干扰，可同时打开；
- 存档入口按钮仍只对管理员显示，小地图入口对所有人显示。

## 4. 玩家传送设计

### 4.1 交互流程（管理员）

```text
管理员模式（isRoomAdmin()）下：
1. 点击玩家圆点 → 选中（描边 + 状态条"已选中 XXX"）
2. 点击目标格子：
   - 格子可通行 → 弹出确认（toast 级确认，防误触）→ teleportCharacter
   - 格子不可通行 → 提示"该位置不可通行"，拒绝
3. 取消选中：右键 / Esc / 再次点击同一玩家
4. 目标玩家位置更新由原版同步链路自动广播（约 1 秒），小地图随之刷新
```

- 传送自己同样支持（管理员也是玩家）；
- 目标不可通行时提供"强制传送"按钮（可选，对应原版管理员超能力语义，第一版可先不做）；
- 选中态 + 目标格在画布上以颜色区分（可传送=绿色，不可=红色），减少误操作。

### 4.2 权限与安全

- 发送端：`assertRoomMapAction()`（聊天室 + 地图房 + 管理员）+ 原版函数自带 `ChatRoomPlayerIsAdmin()` 双重检查；
- 接收端：原版 `ChatRoomCharacterIsAdmin(sender)` 校验，伪造消息无效；
- 不引入任何新权限体系，完全沿用房间管理员语义。

### 4.3 风险与降级

| 风险 | 应对 |
|---|---|
| 旧版 BC 无 `ChatRoomMapViewTeleport` | 能力检测 + fallback 手发消息；若接收端也无处理逻辑（更旧版本），功能静默不可用，UI 提示"当前版本不支持传送" |
| 目标玩家离线/离开房间 | 传送消息静默丢失。可选增强：发送 2 秒后检查目标位置未变化则提示（第二轮迭代） |
| 传送无回执 | 原版设计如此，位置由目标自己广播；接受 ≤1 秒延迟 |
| 位置在墙里 | 设计如此（穿墙语义）：落墙后由原版碰撞系统自动弹推至邻近可站格；UI 提前红色警示落点性质。极端情况（四周全墙）玩家会停在墙内，属原版行为，不做额外处理 |
| Hidden 消息大小 | Dictionary 仅一个条目，远低于服务器限制，无风险 |

## 5. 测试计划

- **单元测试（沿用 tests/ 现有 runner）**：
  - `buildMapGridSnapshot`：用真实导出串的 Tiles/Objects 构造样例，验证墙/半墙/障碍/门/水的判定；
  - `teleportCharacter`：权限断言（非管理员拒绝）、边界校验（越界拒绝）、消息结构（fallback Dictionary 格式正确）；
- **手动测试**：
  - 地图房内开小地图：缩放/拖拽/玩家位置刷新；
  - 管理员编辑地图后小地图底图自动刷新；
  - 管理员传送他人/自己，验证全房间位置同步；
  - 非管理员看不到传送交互。
